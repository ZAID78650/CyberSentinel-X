# Resilience Layer

CyberSentinel-X's resilience tooling: **What-if Attack Simulator** (with a
**live scenario replay** through the real detection pipeline), **Model
Center**, **Compliance Center**, and the **Cyber Resilience Score**. Every
number here is computed from real system data or from a clearly-labeled
simulation — nothing is fabricated or presented as a confirmed live metric.

All routes are under `backend/app/api/routes/soc_tools.py`, services in
`backend/app/services/resilience.py` (tests: `backend/tests/test_resilience.py`).

---

## 1. What-if Attack Simulator

**`POST /api/soc/simulate`** — project a deterministic kill-chain from an asset
entry point and show the risk impact of the mitigation stack.

```json
{ "asset_id": "ast-customer-db", "starting_stage": "Initial Access" }
```

Response fields:

- `kill_chain[]` — up to 6 stages with per-stage `probability`, `exposure`, and
  `controls` (the mitigation stack). Every stage is labeled `state: "SIMULATED"`.
- `risk_before` / `risk_after` — risk derived from real asset criticality,
  real incident count on that asset, and the stage depth; after applies the
  controls. Verified live: `51.0 → 7.7` (`-85%`), affected assets `9 → 2`.
- `incidents_on_asset` — real incidents referencing the asset.
- `note` — explicit "SIMULATION … not a confirmed attack" disclaimer.

The simulator never touches real systems; it only reads asset metadata and
incident history, then applies the deterministic kill-chain model.

### Live scenario replay — watch detection happen

**`POST /api/soc/simulate/run-live`** — re-ingests the projected kill chain as
**clearly-labeled SIMULATED events** through the *real* detection engine
(rules + Isolation Forest + threat intel). Every event carries
`source="SIMULATED"`, so provenance is never mixed with live telemetry or
UNSW-NB15 flows.

```json
{ "asset_id": "ast-app-server", "starting_stage": "Reconnaissance" }
```

What happens, deterministically:

1. A stage→event map converts the 6-stage chain into ~15–20 realistic events
   (PORT_SCAN, LOGIN_FAILURE burst, PRIVILEGE_ESCALATION, DATABASE_ACCESS,
   DATA_EXFILTRATION, …) with recent, watchable timestamps.
2. `ingest_batch()` runs each event through the production detection engine —
   the engine itself decides what is anomalous (the replay is not pre-labeled
   anomalous).
3. The Detection Agent correlates the anomalous cluster into an **alert** and
   **incident**, broadcast over WebSocket (`new_event`, `new_alert`,
   `new_incident`) so the Live Events page and dashboard update in real time.
4. The orchestrator pipeline runs on the incident: investigation → threat
   intel → risk → response → report → **Attack DNA + prediction + evidence**.
5. `SIMULATION.LIVE` is written to the audit log.

The response includes a full `timeline[]` (event type, severity, anomalous
flag, detection reason, kill-chain stage) so the UI can show exactly which
signals the engine fired on. Verified live: 15–18 events, 100% flagged,
alert + incident created, DNA/evidence generated by the pipeline.

## 2. Model Center

**`GET /api/soc/model-center`** — the production detection model and its
measured metrics:

- `model` — IsolationForest + deterministic rules, version, hyperparameters
  (`contamination 0.05`, `n_estimators 100`, `random_state 42`), live fit count.
- `evaluation` — from `app/ml/evaluate.py::run_evaluation()`: a labeled corpus
  (337 events: 77 attack, 260 benign) scored through the **production detection
  engine** in an isolated DB. Verified: accuracy 98.81%, precision 93.85%,
  recall 100%, F1 96.83%, FP 4, FN 0.

The `note` field states explicitly that metrics are measured on a labeled
corpus through the production engine — not training-time numbers.

## 3. Compliance Center

**`GET /api/soc/compliance`** — maps **observed MITRE techniques** (from real
`IncidentMitreMapping` records) to controls across three frameworks:

| Framework | Controls covered | Posture |
|---|---|---|
| NIST CSF | 4 / 5 | 80% |
| CIS Controls | 6 / 7 | 86% |
| ISO 27001 | 6 / 6 | 100% |
| **Overall** (weighted) | | **88%** |

Each framework returns `gaps[]` with the missing techniques per control
(e.g. NIST `identify` missing `T1589 · T1595`) so posture is actionable.
The method ("controls covered by observed techniques / total mapped controls")
is returned with every response.

## 4. Cyber Resilience Score

**`GET /api/soc/resilience`** — explainable weighted mean of six factors, each
computed from real records and returned with its `evidence` string:

| Factor | Weight | Basis |
|---|---|---|
| Threat Exposure | 20% | share of incidents not HIGH/CRITICAL |
| Asset Risk | 20% | inverse of average asset risk |
| Detection | 25% | measured accuracy on labeled corpus |
| Response Readiness | 15% | resolved/closed ÷ incidents |
| MITRE Coverage | 10% | observed techniques ÷ library (3× weighted for small corpus) |
| Supply Chain | 10% | baseline until an SBOM is ingested (labeled LOCAL) |

Labels: `STRONG ≥ 75`, `MODERATE ≥ 55`, else `WEAK`. Current real value:
**47.8 / WEAK** — driven by 16/20 HIGH/CRITICAL incidents and only 1/20
resolved. The score answers "why" and is honest: improving it means resolving
incidents and reducing exposure, not tuning the dashboard.

## Frontend

- **Attack Simulator** — `/attack-simulator` (Resilience group): asset + stage
  pickers, before/after risk gauges, per-stage kill chain with controls, and
  a **Run live scenario** button that replays the chain through the real
  pipeline and shows the event-level detection timeline (ANOMALY flags per
  event) with links to the incident's War Room.
- **Model Center** — `/model-center`: model card, confusion-matrix stats,
  accuracy gauge, precision/recall/F1.
- **Compliance Center** — `/compliance`: overall gauge, per-framework cards
  with coverage bars and gap lists.
